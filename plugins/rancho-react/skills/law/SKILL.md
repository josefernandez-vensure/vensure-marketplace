# React Law

A tree bound here is a React micro-frontend that the PrismOne shell mounts. It consumes the HTTP contract of the core law (§5) through a client generated from the server's committed OpenAPI document; what the user may do is the server's answer, every time. Its checks enforce most of how the code is built. This law states what they can't: how to use the codebase as the reference, and the decisions neither a check nor an example shows.

## 1. The codebase is the reference

- The tree's `CLAUDE.md` has a `## Reference` section. For each kind of code, such as a query, a store, a form, an edit form of a versioned resource, a route or a test, it names the implementation to follow. Before writing code of a listed kind, read its reference and match it: structure, naming, and tests.
- Reference code is held to this law. Where the two disagree, the law wins: say so, and fix the reference in the same change or report it.
- For a kind with no reference yet, build it from this law. It is reviewed as the new reference, and its path is added to the list in the same change.
- Code not on the list is precedent, not reference. Follow it where the law and the references are silent and a second occurrence confirms it. Otherwise ask.

### The checks

The tree carries the checks of the `rancho-react` template: `eslint.config.js` with its own rules (`eslint/`), the strict `tsconfig.json`, `scripts/check.mjs`, and the tests.

- A failing `npm run verify` is the law speaking: fix the code, never the check. Don't relax a check, skip a test, or loosen `tsconfig.json` to get past one.
- A suppression names its rule and gives its reason; a `@ts-expect-error` names its issue. A check you believe is wrong is reported, not edited.
- The lists the checks name (identity packages, presentation packages, stylesheets, telemetry calls, nested-credential claims) live in `eslint.config.js`. Extend a list there, never by suppressing a rule.
- A rule a check can catch gets its check in the change that introduces the first code it governs, proven to fail on a violation.

## 2. Stack

React 19 · Vite · TypeScript (strict) · Prismatic (`@prismhr/components-react`), with Syncfusion only for the grid its grid components host · TanStack Query · React Router · Zustand · React Hook Form + Zod · VensureOne IAM (`@vensure-devops-qa/vensureone-iam-react`) · single-spa · a client generated by `@hey-api/openapi-ts` · Vitest + React Testing Library · MSW · Playwright · ESLint 9, type-aware · npm

- The organization's packages come from GitHub Packages; `.npmrc` reads the token from `NODE_AUTH_TOKEN` and never holds one.
- When the server's contract changes, copy its committed OpenAPI document to `openapi/v1.json`, run `npm run generate`, and commit the output.

## 3. Structure

`src/app/` is the composition root (the shell's lifecycles, providers, the route tree and its routes), `src/features/<feature>/` one user-facing capability, `src/shared/` what two or more features use, `src/generated/` the generator's output.

- A screen that needs two features is a route that renders both, never a feature that reaches into another.
- Promote to `shared/` on the second consumer, never in anticipation of one. The exceptions start in `shared/lib/`: the identity module, the API and query clients, the problem-details parser, and the client-state registry.
- A feature covering the same concept as a server module reuses its name. The two trees share vocabulary, not shape: a module may have no feature, and a feature may read several modules or none.

## 4. Server state

- The TanStack Query cache is memory only: never persisted, so it dies with the tab.
- Server data is never copied into a store or component state: derive from the query. A dialog holds the id of what it opened, never the record. An edit form is the exception (§5).
- Parse every response through its generated schema in the query or mutation function, so everything the application holds carries its data class.
- A mutation declares its invalidations, through the key factory of every resource it changes. A mutation that leaves stale data on screen is incomplete.
- A mutation is retried only when it carries an idempotency key, made once per intent and sent with every attempt.
- A screen that needs a total or an aggregate gets it from the server, never by loading every page.

## 5. Forms

- Every form has a Zod schema that mirrors the server's request constraints; where they differ, the server is right. No validation outside the schema.
- Server errors are shown, and a problem's field errors land on their fields, not only in a banner.
- An edit form of a versioned resource is mounted once its query has loaded and takes the resource as its default values, `etag` included. It sends as `If-Match` the etag its values came with, never the query's current one. It resets only after its own write (to the values written and the etag returned) or a `412` (to the latest values, telling the user someone else changed them). A refetch never touches a form the user is editing: never feed it through `values`, and never reset with `keepValues` or `keepDirtyValues`. A `412` is never retried.

## 6. Components

- Features and `app/` use Prismatic directly. A component never wraps a Prismatic component only to forward its props or restyle it: there is no second design system. A feature component that composes Prismatic components to express domain meaning is a feature component.
- A gap in Prismatic (a component, variant or behaviour it lacks) is an issue filed with its owners. Until it is filled, compose its public components and tokens, and never reach into its internals.
- Layout Prismatic has no component for goes in `src/app/layout.css`, using only Prismatic's tokens.
- Every interactive element is operable by keyboard and has an accessible name. The axe test supports this rule and does not satisfy it: review still carries it.

## 7. Routing

- Route params and search params are parsed through the generated parameter schema before anything uses them, or, for client-only state, through the client-state registry.
- A route file is thin: parse its params, and compose feature components. Logic belongs in a feature.
- Authorization is never inferred from route structure. Hiding UI is not access control.

## 8. The shell's session

The PrismOne shell signs the user in and owns the session. The application reaches it only through `src/shared/lib/identity.tsx`.

- The application never runs a sign-in flow and never refreshes a token. A `401` asks the shell to sign the user in, once; a `403` is a final answer, shown as a permission error.
- The signed-in user's claims and profile may be read for display, within their own session, and for nothing else.
- What the application needs from Enterprise Security (its service name, permissions and menus) is declared in one place, the identity module's options, and is the narrowest it needs.
- Every key the application writes to browser storage goes through `appStorageKey`, so sign-out clears exactly what the application wrote. Sign-out clears the query cache and that storage, then hands over to the shell's sign-out, which ends the provider session.
- The bundle holds no secret. A client id may be in it.
- An application not mounted in the shell (a standalone sign-in, its own token store) has no rules here yet: stop and ask.

## 9. Errors

- A failure is shown through `ProblemMessage`: a problem's `title` only for a type the document's `x-problem-types` marks user-facing, never its `detail`, and always its trace id, so a report can be joined to the server's trace.
- The root route declares an error element, and a route declares its own wherever a failure should take down no more than that screen. A render error never blanks the application.

## 10. Data in the browser

The core law's data classes apply unchanged. The checks keep confidential, restricted and unclassified values out of URLs, browser storage and the telemetry calls they name; a value takes its class only from a generated schema or the client-state registry.

- A registry schema accepts only a closed set of values: an enum, a literal, a boolean, a bounded number, a string of a fixed format that carries no data, or arrays and objects of those.
- URLs and storage are inside the authenticated boundary only while the document's referrer policy sends no path to another origin (`strict-origin-when-cross-origin`, the browser's default, or stricter). The shell serves the document: declare this to its owners, as you declare your grants.
- A telemetry, analytics, session-replay or error-reporting SDK scrubs classified values from what it captures by itself (breadcrumbs, form fields, request bodies): its defaults are wrong for this domain. The first such SDK adds its calls to the checks' list and its scrubbing test.
- The client never assembles an export of sensitive data out of paged reads.

## 11. Tests each kind of code needs

The template's tests already prove the client-wide behaviour: a `traceparent` on every call, the `401` and `403` handling, the query client's retry rule, sign-out, how a problem is shown, the root error element, and axe over every route, which fails when a route isn't listed in it. Write these yourself, following the reference tests:

- A component that renders a query: its loading, error and, for a list, empty state. Where a route's loader moves those states to the route, the route's tests carry them.
- A form: a validation failure, and a server failure whose field errors appear on their fields.
- An edit form of a versioned resource: it sends the etag of the values it was last reset from; a second save after its own succeeds; a refetch while the user edits changes neither their values nor that etag; a `412` refetches and is not retried.
- A retried mutation: every attempt of one intent carries the same idempotency key.
- A route: add it to `tests/routes.test.tsx`.
- A telemetry or error-reporting SDK: a known classified field is scrubbed from a captured event.

Mock the network with MSW, through the application's real client. Query by role and accessible name; `data-testid` is a last resort, with a comment naming the element that has neither. Don't assert on class names, DOM structure or component internals, and don't write a test that proves only what the type checker proves. Playwright covers critical user journeys only.

## 12. Not yet covered

Real-time push (SignalR, `WebSocket`, `EventSource`) and an application outside the shell have no rules here yet. Before opening the first real-time channel, or running outside the shell, stop and ask.

## 13. Verification

`npm run verify` passes before a change is done: lint, the type check, the tests, and `scripts/check.mjs`.
